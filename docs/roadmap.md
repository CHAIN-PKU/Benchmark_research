# 路线图

日期：2026-11-12 · 作者：Claude Code · 状态：预热阶段，待陈润材确认

## 目标

多发 NeurIPS / ICML / ICLR。主线是针对垂直领域搭 benchmark，重点是把 benchmark 基础设施的搭建全流程学会、做扎实；辅线是数据归因、数据合成、后训练，它们都围着 benchmark 转。

## 主线：一个 benchmark 从零到发表的八步

每一步写：做什么、需要什么基础设施、我们现在有没有。

| 步骤 | 做什么 | 需要的基础设施 | 现状 |
|---|---|---|---|
| 1. 选垂类、定义能力 | 说清要测哪种能力、为什么现有 benchmark 测不出来 | 文献检索、研究笔记 | 有研究 wiki（PR #6）；论文检索工具待选品 |
| 2. 找题源 | 从真实来源出题（真实提交、真实数据、真实 issue），天然带判分信号 | 数据抓取、去重 | 缺 |
| 3. 造题、冻结环境 | 每道题连同运行环境一起固定下来，谁跑都一样 | 容器（Docker）、依赖锁定 | 缺：本机没有 Docker |
| 4. 判分器 | 优先用确定性判分（测试、精确匹配）；必须用模型当裁判时，加输出格式校验和防注入 | 测试框架、裁判提示词 | 缺 |
| 5. 难度标定 | 用便宜模型和强模型各跑几次，按通过率分 easy / medium / hard | 统一的评测运行器、多模型接口 | 缺 |
| 6. 防泄题、防刷分 | 题面只写症状，不泄露判分条件；按 BenchJack 的 V1–V8 自查；查训练语料污染 | BenchJack、n-gram 去污染 | 有 BenchJack skill（PR #4） |
| 7. 跑评测 | 所有模型同样的轮数、时间和环境；环境故障导致的失败单列，不算模型的分 | 评测框架（Inspect AI 或 lm-evaluation-harness）、结果存档 | 缺；框架对比见 docs/benchmark-frameworks.md（PR #5） |
| 8. 分析与发表 | 排行榜、逐题读模型输出找失败原因、数据说明书、复现包；写论文、画图 | 论文写作和画图 skill | 有 ml-paper-writing、academic-plotting（PR #4） |

### 我们以前做题踩过的坑（写进流程，不再重踩）

- **自己合成或反向注入的题太容易**：便宜模型 grep 一次就过了。题要从真实来源倒推。
- **题面写得太精确等于泄题**：把判断条件写进说明，模型照着做就过。题面只写症状。
- **跑一次不算数**：真实失败率不高时，单次通过是正常现象，要重复跑多次估通过率，才能定难度。
- **最大的损失来自环境故障，不是模型**：预算截断、权限不足、令牌用完、评分环境不一致。这类结果要识别出来，不计分。
- **各模型的评分环境必须一致**，否则分数不可比。

## 辅线：怎么和 benchmark 接上

| 方向 | 和 benchmark 的关系 | 第一步 |
|---|---|---|
| 数据归因 | 回答「模型在这道题上的对错，是训练数据里哪些样本造成的」，能把 benchmark 的失败归因到数据 | 网上没有现成 skill，先读 TRAK / 影响函数的代表论文，写一个我们自己的 skill |
| 数据合成 | 针对 benchmark 暴露的短板合成训练数据。注意：合成数据只用于训练，不能拿来当测试题 | 先做文献调研，记进研究 wiki |
| 后训练 | benchmark 的判分器可以直接当强化学习的奖励函数（可验证奖励），benchmark 也是后训练效果的验收尺子 | Orchestra 的后训练 skill（TRL、GRPO、verl）可以按需引入；需要 GPU 服务器 |
