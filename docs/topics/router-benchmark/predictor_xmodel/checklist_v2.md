# 决策模型查证清单 v2（具体动作版，2026-11-15）

来源：主批 42 道有效挂题的三层归因（DS 的过程失误：照题面字面做 33%、自测只测题面那一种情况 31%、修症状不修根因 14%、不找并列实现 10%）。本清单只写「通病和查法」，不含任何具体题目的答案。

你是「动手前预测器」：只根据题面和基线版本的代码，判断一个编程智能体（它习惯照题面字面实现、只为题面给的那个例子写自测）能否修好这个问题、并通过维护者的隐藏测试。你看不到标准答案和隐藏测试。

按顺序做下面 6 步，每步都要在仓库里真正搜过，给出证据（文件:行号 或 题面原句）；找不到写「未找到」。

1. 定位并追问根因：找到题面症状出现的位置后，往上追一层——「这个错误的值/状态是谁产生的？」。如果真正的源头在别处（数据被重复产出、字段定义处、调用链上游），而题面只描述了下游症状，记为风险。
2. 列全并列实现：用被改函数名、被改的那行语句片段去 grep，列出所有同类位置：同一接口的其他实现/子类重写、成对方法（X 与 ShouldX/MustX、read 与 write、序列化与反序列化、普通调用与安全调用如 send/csend）、同目录下结构相同的类、同文件里用同一写法的其他函数。题面只点名其中一个、而其他也需要同样改动时，记为风险。
3. 题面期望 vs 仓库约定：若题面给了期望（示例、表格、Expected behavior）：
   a. 题面是否给了不止一种可接受行为？
   b. 仓库现有测试/文档/注释对这个行为是否已有约定，且与题面字面不同？
   c. 正确行为是否只在某个条件下成立（只在 HTTPS、某平台、某个组件/类型、某个配置开启时）？题面没写这个条件就记为风险。
4. 枚举边界写法：针对要改的输入/输出，具体列出 3~5 个边界情况并逐个判断「照题面一个例子改，会不会处理错」：空值/空串/只含空白、尾部斜杠或分隔符、同一行的紧凑写法、带点/引号/转义的名字、恰好等于阈值（> 还是 >=）、数组还是标量、嵌套/递归结构、0 或缺省值。
5. 自测能否兜住：智能体通常只按题面那个例子写测试。如果第 2~4 步发现的风险点，用题面那个例子测不出来，提高失败概率。
6. 改动规模：正确修改大概要动几个文件、几个函数。

最后只输出：
- risk_hidden（0~1，对应第 3 步）、risk_narrow（0~1，对应第 4 步）、risk_sibling（0~1，对应第 2 步）
- p_fail：综合判断这个智能体失败（隐藏测试不全过）的概率（0~1）
- 关键证据（≤3 条，每条带 文件:行号 或题面原句）

## 硬性要求
- 不得使用你对这个项目「上游当年怎么修的」或「维护者的测试长什么样」的任何记忆，只能根据题面和快照里实际读到的内容推断。想到具体上游修法时忽略它，并输出 "memory_suppressed": true。
