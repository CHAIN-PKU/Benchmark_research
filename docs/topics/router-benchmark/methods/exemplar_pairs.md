# DS 预测 few-shot：6 组对照（挂 vs 过）

## 对 1（Go / caddy：同仓库，都是"改默认行为"）
- 挂的题：caddy-6115（0/2）；题面：lb_policy cookie 的粘性 cookie 应默认带 Secure 和 SameSite=None；正确修复：只在请求走 TLS、或来自可信代理且 X-Forwarded-Proto=https 时才加这两个属性，明文 HTTP 仍保持原样；落差：题面说"默认"，没提条件分支，也没提可信代理变量这个已有机制。
- 过的题：caddy-5870（2/2）；题面：DELETE 不存在的配置路径应返回 4xx；足够：现象、复现步骤、期望状态码都写明，改动是在已有 PUT/PATCH 分支旁补一个同形的 404 分支。
- 决定性差别：挂的题字面要求"无条件"，但代码库里已有 TLS/可信代理判断机制，直接照字面改会错；过的题字面要求与代码里已有同类分支完全一致。

## 对 2（Java / gson：同仓库，都是"某个 API 行为不对"）
- 挂的题：gson-1100（0/2）；题面：setDateFormat 后序列化 null 的 Date 字段抛 NPE；正确修复：write 里判 null 写 nullValue，同时 read 侧也要接受 null 并返回 null（原先读到非字符串就抛异常）；落差：题面只给了写出方向的堆栈，读回方向要同步改没有提。
- 过的题：gson-1093（2/2）；题面：JsonWriter.value(double) 在 lenient 模式下也应像 value(Number) 那样允许 NaN/Infinity；足够：题面贴出了两个方法的对照代码，改法就是把 value(double) 的判断对齐成 `!lenient && ...`。
- 决定性差别：挂的题只给出症状的一半（写），对称的另一半（读）要靠读代码里 DefaultDateTypeAdapter 的 read/write 成对结构才发现；过的题把"对齐哪两处"直接贴在题面里。

## 对 3（C++ / fmt：同仓库，都是格式说明符问题）
- 挂的题：fmt-3750（0/2）；题面：`{:LX}` 本地化格式总输出十进制；正确修复：重写带分组的 write_int，让 hex 大小写、bin、oct、chr 及 '#' 前缀、八进制前导 0 计位等都走正确分支，非法类型要报错；落差：题面只举了 X 一个例子，没说其余进制/前缀/精度的行为。
- 过的题：fmt-3248（2/2）；题面：对齐符和 0 同时出现时 0 应被忽略，给了两个"期望/实际"；足够：引用了标准原文，改法是 on_zero 里遇到已设对齐就直接返回。
- 决定性差别：挂的题"一个例子"背后是一个要覆盖多种进制和前缀组合的代码路径，动手前看 write_int 的分组分支就能知道只支持十进制；过的题规则单一、期望输出已逐条给出。

## 对 4（Ruby / rubocop：同仓库，都是 cop 误报）
- 挂的题：rubocop-13560（0/2）；题面：Style/FileNull 把普通字符串 'nul' 当成 NUL 设备；正确修复：不是简单忽略 'nul'，而是仅当同文件里还出现 '/dev/null' 才报 'nul'，'NUL:' 仍总是报；落差：题面写"忽略 'nul'"，没说这个折中规则，且 REGEXP 本意是同时检测 Windows 的 NUL。
- 过的题：rubocop-13362（2/2）；题面：带 #@var 插值的字符串被当成无插值导致 RedundantFreeze 误报；足够：题面给出输入、期望无报错，改法是在已有"有无插值"判断里补充 ivar/cvar/gvar 节点类型。
- 决定性差别：挂的题字面要求（'nul' 不再报）与 cop 的存在目的（检测 NUL）冲突，需要折中判断；过的题字面要求与 cop 目的一致，只是漏掉几种节点类型。

## 对 5（Rust / uutils：同仓库，都是对齐 GNU 行为）
- 挂的题：uutils-6377（0/2）；题面：仅一行，复制了 GNU env 手册里的 `--ignore-signal[=SIG]`；正确修复：新增选项、逗号分隔解析、信号名大小写转换、无参时的处理、非法信号以 125 退出并报 "invalid signal"、实际用 sigaction 忽略信号并在 spawn 前生效；落差：题面没给语义，这些全靠对 GNU 行为的了解和读 env.rs 现有结构。
- 过的题：uutils-6682（2/2）；题面：`mkdir -p` 对已存在且无权限的目录不应失败，给了命令、报错信息和 GNU 的对照结果；足够：问题定位到"已存在目录不该再 chmod"，改法是让 create_dir 返回是否新建，只有新建才 chmod。
- 决定性差别：挂的题是"空白新功能"，要自己补出整套接口和边界；过的题是有完整复现和期望的 bug，修复点唯一。

## 对 6（JS / axios：同仓库，都是 http 层小改动）
- 挂的题：axios-6539（0/2）；题面：SSRF 漏洞，相对路径 `//google.com` 被当成协议相对 URL 发往别的主机，并给了"期望报错"与"期望拼接到 baseURL"两种预期；正确修复：改共享辅助函数 isAbsoluteURL，不再把以 `//` 开头视为绝对 URL（必须带 scheme）；落差：题面没点名这个函数，且该函数注释里明确把协议相对 URL 当绝对 URL，是已有约定，题面还给了两个互相矛盾的期望。
- 过的题：axios-5892（2/2）；题面：响应头 content-encoding 为 GZIP 时不解压，希望不区分大小写；足够：头名和现象明确，改法是 switch 前统一转小写，一处改动。
- 决定性差别：挂的题的根因在一个被多处复用且带显式约定的辅助函数里，题面只描述了下游症状；过的题症状点和修改点是同一处，没有既有约定要推翻。
