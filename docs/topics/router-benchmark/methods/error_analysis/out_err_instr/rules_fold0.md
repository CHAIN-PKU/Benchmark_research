1. 先看档案是否把根因和修改点定位到少数文件、少数几处，并且有同类先例或现成写法可照抄。若有，不要因为题面看起来涉及多个概念、有多种可能解释而抬高失败概率。若档案只给出方向、没有明确落点，才维持中等判断。

2. 看档案是否列出多处并列、对称的实现（如同类的 read/write、多个并列子类、平行的读写器或拷贝路径），而题面只点名其中一处。只要看到这种「题面只提一处、档案另有并列处且无测试覆盖」的情况，就抬高失败概率，因为智能体倾向只修题面所指之处。

3. 看档案是否提到存在两种或多种都可行的修法，以及隐藏测试可能断言的接口约束（如某个类不得修改入参、必须改字段定义而非调用方）。只有看到「多种修法并存且测试断言形式无法从题面推断」时才抬高；若档案已指出某种做法最稳妥或唯一合理，则不要因为存在备选方案而抬高。

4. 问：隐藏测试需要的是哪个具体行为？若题面已给出复现脚本或明确的期望行为，就按「测试只断言这一点」来估计，不要因为档案里列出的细枝末节（参数名、边界冲突、其他场景）而抬高。若题面只描述了现象（如静默出错），而合理的验证方式是抛出特定异常、给出具体消息，则抬高，因为智能体难以猜中精确的错误类型和文案。

5. 看测试依赖的外部接口是否存在二选一且无法从题面推断的选择（如时钟取法、mock 点、被打桩的函数）。看到测试会 mock 这类接口、选错必挂时才抬高；若测试只是源码比对、往返序列化、加一个同类用例等宽松形式，则压低。

6. 看题面或档案对测试标准的描述：若现有测试不断言顺序、细节，或隐藏测试只是新增一个简单用例，就不要因为实现细节有多种写法而抬高。

7. 不要因为问题涉及并发、栈深、转义、跨语言域、编译器等听起来「深」的领域而抬高。只看档案是否已查明根因、修法是否局部（几行、一两处）、是否有现成参考实现；三者满足则压低。

8. 最后做一次核对：想抬高时，必须能指出一个具体的失败机制（漏改的并列处、选错的接口、猜不到的报错文案）；指不出来，就按档案已定位的小范围改动来判低。
