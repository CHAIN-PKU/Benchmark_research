1. 先看档案是否已把根因定位到具体位置、且题面期望明确。若定位清楚、改动局部（只涉及少数几处），并且你能说出隐藏测试大概率只复现题面场景，就不要因为「看起来要考虑很多边界」或「档案罗列了许多边界情况」而抬高；档案中提到的边界，只有在能指向某条现有测试或题面明确要求时才算数。

2. 对档案里列出的顺序、计数、负值、其他命令、false/null 之类的边界，逐个问一句：「隐藏测试会不会真的断言它？」若题面没提、现有测试也没覆盖，就不要因为这些边界存在而抬高；只有题面或现有测试已显式涉及时才抬高。

3. 当档案指出的修法有先例（相邻代码已有类似处理）或有「最简规则」即可通过时，不要因为理论上存在更完整的实现而抬高；判断「最简修法能否通过题面场景的断言」，而不是「完整方案要多大」。

4. 查看档案中现有测试的期望值和输入形态（如根路径、尾部换行、行号补偿、数字格式、规范化行为）。看到现有测试的期望与题面修复后的行为存在冲突，或修复会顺带改变输出格式、规范化结果，才抬高：隐藏测试往往会更新这些断言，DS 容易漏掉这类连带变化。

5. 看到档案提到多种可能的期望形式（整数 vs 浮点、不同格式说明符的歧义）、或要求精确匹配某种格式时，才抬高，并按「必须逐字符精确匹配」来评估，不要当作小改动。

6. 核查题面的链接、标题、环境描述是否会把 DS 引向错误位置或只对单一平台生效的补丁。看到题面引用的模块与真正出错处不同、档案里存在容易被误改的相似示例，或平台限定的表述而复现步骤本身与平台无关（测试在别的平台上运行）时，才抬高，并把这类误导线索当作主要风险。

7. 当修复表面上只有一行，但改动会让另一类输入（如带参数的路由、被解耦后失去信息的路径）行为变化时，才抬高：要追问「这个改动对其他输入类型是否仍然成立」，检查底层函数对这些输入是否本来就缺少所需信息。若只影响题面所述的那一类输入，则不要抬高。

8. 最终判断前做对照：抬高的理由必须是某条具体的「现有测试冲突、格式歧义、误导线索、连带影响」证据；若理由只是「改动涉及共享状态」「可能还有别的边界」「需要多处理几种情形」这类泛泛担忧，就保持较低，不要抬高。
