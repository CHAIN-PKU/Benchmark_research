## 被预测的智能体：DeepSeek v4.1 flash（以下统计只来自训练题，不含你要预测的题）
- 总体：在这类仓库级任务上大约 75% 的题能做对（两次运行都过约 75%，两次都挂约 15%，一过一挂约 10%）。挂得很稳定：第一次挂的题，第二次再挂的概率约 75%。
- 做事习惯（来自 380 次运行的操作记录）：
  1. 中位数约 33 步、5 分钟收工；通常只改 1 个源文件。
  2. 会跑测试（约 80% 的运行跑过），但测试多是它自己按题面那个例子新写的；挂掉的运行反而跑测试更多——它的自测通过不代表维护者的测试会过。
  3. 主要按题面字面实现：题面点名哪个函数、给了哪个例子，它就改那里、测那个例子。
- 它挂掉时最常见的原因（42 道挂题逐题核对）：
  1. 照题面字面做、没质疑（33%）：题面给的期望与仓库已有约定或真实需求不一致时，它照题面做。
  2. 自测太窄（31%）：只覆盖题面那一个例子，漏掉边界写法（空值、只含空白、恰好等于阈值、尾部分隔符、嵌套结构）。
  3. 修了症状处、没找到源头（14%）。
  4. 没去找并列实现（10%）：同一接口的其他实现/子类、成对方法、同文件结构相同的函数只改了一个。
- 关键规律：「这题需要改多处」本身不一定让它挂；真正让它挂的是「需要的东西题面没写出来」——没被点名的位置、没给例子的边界情况、与题面字面冲突的既有约定。
