# DeepSeek 动手前判断经验（本批 86 题，整体挂率 24%）

## 一、DS 什么时候挂、什么时候过

只写两侧挂率差距大的信号（基线 24%）。

**1. 题面期望含糊，或要改旧契约：挂 9/20（45%）；期望唯一且只需新增/保持：挂 9/55（16%）**
- 挂：`laravel-48573`，题面补丁写 `>`，但现有锁测试约定"恰好 TTL 秒即过期"，要用 `>=`，DS 照抄 issue diff。
- 过：`gin-2121`，题面直接给出 3 行修法且与测试无冲突，抄即可。

**2. 题面只给一个例子，同类变体要自己补全：挂 12/49（24%）；档案称无同类重复：挂 4/25（16%）**
- 这条整体差距不大，真正拉开差距的是"必须自己枚举同类全集"这一子类。
- 挂：`php-cs-fixer-7663`，只给一个例子，但 `$blockSignatureFirstTokens` 不含 `T_DO`，无花括号 do-while 要枚举 do/elseif/else。
- 过：`hugo-12768`，只有一个大小写敏感的正则，无并列解析路径，加 `(?i)` 即可。

**3. 修复落点有多个诱人位置：挂 11/37（30%）；症状点即修改点：挂 9/38（24%）**
- 挂：`caddy-6345`，题面链接指向已支持的 `tls internal`，DS 易改错指令，应改的是 `acme_server`。
- 过：`gin-4003`，栈直接指向 `gin.go:693` 的 `len(t)-1`，修法唯一。

**4. 题面带误导线索（现成补丁、平台字样、规范链接）：挂 5/14（36%）；平台无关、给出可运行复现：挂 16/64（25%）**
- 挂：`bat-2650`，标题写 "on Windows"，但复现与平台无关，DS 把修复限定在 Windows，测试在 Linux 上跑。
- 过：`jekyll-8167`，题面直接给出完整正则，改两行常量。

**5. 状态/幂等/作用域栈/边界数值约束，档案只当旁注：挂 13/47（28%）；状态约束已被档案讲透、单点改动：挂 5/25（20%）**
- 挂：`prometheus-10633`，float64 用 `'g'` 会输出 `1e+06`，测试精确比对字符串。
- 过：`gin-4003`，单行边界，无多阶段交互。

**6. 需自行设计公开 API/输出格式：挂 3/7（43%）；接口由题面或现有 CLI 决定：挂 18/77（23%）**
- 样本小，只作弱信号。
- 挂：`fmt-3863`，题面表格的输出没有引号，而规范要求 `s` 加双引号。
- 过：`jq-2598`，输出期望已给出，可逐字对照。

**7. 最小修法会丢功能（档案列出取舍）：几乎必挂**
- 挂：`fmt-3750`，回退无分组最省事，但 hex/bin/oct 在 locale 下仍要分隔符，14 家里 12 家没做对。
- 过：`hugo-12768`，最小修法就是正确修法。

**8. 改动牵连多文件，且牵连面未被档案核实：挂 7/30（23%）；单文件，调用点已核对：挂 12/46（26%）**
- 这条几乎没有区分度，不要用它加分或减分。真正的信号是"牵连面是否被核实"。
- 挂：`gin-3227`，题面和档案都说只改一行，但解耦后 `tree.go` 对带参数路由缺少 tsr 生成。
- 过：`gin-2121`，在 Render 内一处修复覆盖两条路径。

## 二、判断者常犯的误判

### 漏报（给低了，实际挂了）：被"改动小/定位简单"骗了
漏报案例的共同点是根因好找、改动只有几行，判断者因此放松。判断步骤：

1. **先找"小改动但有字面陷阱"的信号**，看题面是否有：
   - 现成补丁与测试约定相反（`laravel-48573`）；
   - 平台字样但复现与平台无关（`bat-2650`）；
   - 链接指向已实现的同名选项（`caddy-6345`）。
   
   命中任一条，就不要按代码量给低分。
2. **档案是否点名了优先级/覆盖关系**，比如 `jq-2728` 的 `NO_COLOR` 与 `-C`。点名了就按"DS 会照字面实现"处理，给高分。
3. **涉及数字、字符串格式化或两个来源的 URL/字符串比较**：要警惕科学计数法（`prometheus-10633`）和尾斜杠规范化（`laravel-46234`）。档案说"大概率不用处理"的边界，常常正是隐藏测试点。
4. **fuzz/崩溃题**：档案若提到输出或行数补偿耦合（`caddy-5404` 的 `NumLineBreaks`），隐藏测试往往还断言附带的输出修正，不能只看 panic 根因。
5. **题面说"只改一行"时，核查被解耦的另一条路径是否也成立**（`gin-3227`）。

### 误报（给高了，实际过了）：被"难、边界多、清单长"吓到
误报案例的共同点是档案已锁定根因，判断者却被风险清单、模板元编程、"开放设计"等措辞推高分数。判断步骤：

1. **先问：档案是否已定位到具体文件/函数，且改动 ≤1–2 文件？** 是的话，边界清单再长也只给中低分。例子：`jq-2750`、`laravel-51195`、`hugo-12448`、`preact-3562`。
2. **仓库内有没有可照搬的现成修法？** 有就降分（`preact-4182` 的 Suspense 钩子参照）。
3. **隐藏测试验的是行为还是接口？** 只验行为（`bat-562` 的文件名被当文件）就不必担心命名不确定。
4. **设计取舍题**：先看有没有简单的全局方案满足题面行为。有且改动局部，就别因"设计开放"给高分（`jekyll-8771`）。
5. **模板元编程题**：只看改动落在几处条件判断上，不看技术难度本身（`fmt-3158`）。
6. **"清单≠覆盖"**：风险清单里的项目，要在题面或现有测试里找到对应的断言证据才算数。

### 对照两类误判的一个关键反例
`bat-1892` 里，判断者以为要猜未知的新方法名而给 0.8；但档案给出了现有测试风格和注入通道，接口可从现有 mapping 推断。判断"API 风险"前，先查档案是否给出了现有测试风格。

### 校准提醒（来自 DS/GLM 当判断者的偏差）
- **易题系统性高估**：`caddy-5626`、`caddy-5870`、`prometheus-10720`、`redis-11631` 都是 0/14 或 1–2/14 没做对，却被判到 0.4–0.6。根因明确、一行修法，不要给 0.4 以上。
- **被无关风险带偏**：`jq-2598` 的 `parser.c` 不重建（构建会重新生成）、`fmt-3272` 的兄弟分支和 wchar，都是无关项。只有能对应到题面行为的风险才计入。
- **查到了却没掂量**：`caddy-6115` 的 `Secure: r.TLS != nil` 是线索，不是与题面冲突，应据此判断要依赖 TLS，给高分（14 家 11/14 没做对）。`preact-2757` 找到了 value 跳过逻辑，仍要考虑修得过窄，不要低于 0.4。
- **"以为简单"导致低估**：`fmt-3750` 里 GLM 以为回退即可而给 0.2，实则回退丢分组。凡档案写明"最小修法代价=丢功能"，一律给高分。

## 三、速查打分顺序

1. 先查是否有"小改动但字面陷阱"（补丁方向、平台、同名链接、格式化、优先级）。有就至少 0.5。
2. 再查最小修法是否丢功能，或题面输出与规范冲突。有就 0.6–0.8。
3. 否则，若档案已定位到唯一根因且改动 ≤2 文件、有现成参照，给 0.05–0.25。
4. 其余情况，按"期望含糊/要改旧契约"（挂率 45%）与"落点多"（30%）两项上调，其他项不单独加分。
