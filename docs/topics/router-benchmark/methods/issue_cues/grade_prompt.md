# 阅卷：这次为什么没过（事后归因，只用于总结特征）

你是阅卷老师。下面给你一道真实的仓库修 bug / 加功能任务的全部材料：题面、维护者的标准修复、维护者的隐藏测试、某个编程智能体实际提交的补丁、以及评测结果（哪些测试没过）。
另外告诉你：在同一道题上，其他 13 个智能体有多少个做对了。

请判断这次提交为什么没通过，并找出**做之前**就能看到的线索。

只输出一个 JSON 对象，字段如下：
- cause：一句话，具体说这次补丁和标准修复差在哪（例如「只改了 X，没改并列的 Y」「错误信息文字与测试要求不一致」）。
- cause_type：从这些里选一个最贴切的：hidden_requirement（题面没写、测试要求的行为）/ narrow_scope（题面举例比正确修法窄，照字面改了）/ sibling_missed（并列位置漏改）/ wrong_location（改错了地方或层次）/ broke_existing（改坏了原有行为）/ incomplete（方向对但没做完）/ format_detail（格式、空白、转义、文字细节）/ other。
- issue_cue：题面里能提前提示这个风险的原文片段（直接引用，≤40 字）；没有就写 "none"。
- issue_cue_pattern：把上面的线索抽象成**不依赖这个项目**的一般规律，写成「题面里出现……时，要警惕……」；没有就写 "none"。
- repo_cue：读修复前的仓库能看到的线索（例如「同目录有一个并列实现」「已有测试断言了具体报错文字」）；没有就写 "none"。
- foreseeable：做之前，一个认真读题面和代码的人能否预见这个风险：high / medium / low。
- why_others_passed：如果多数其他智能体做对了，说说这道题对「做得仔细」的智能体其实不难的原因；否则写 "most_failed"。

要求：只根据给出的材料判断，不要编造材料里没有的内容。
