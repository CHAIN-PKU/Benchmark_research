## 二、三条候选特征（先写成「遇到什么题、仓库里有什么 → 容易挂」）

### F3 隐藏要求（最强）
**题面没写、但正确性取决于它**：要和参考实现（GNU 等）完全一致的行为或报错文字；题面自己写的「期望」和上游做法相反；只在某条件下才生效（如只在 HTTPS 下设 Secure）；多个选项的优先级。
- 失败题里：6 道 —— axios-6539、caddy-6115、rubocop-13560、coreutils-6377、jq-2728、caddy-6345
- 做对的题里：0 道
- 动手前信号（只看题面和仓库）：题面给了具体「期望输出 / 改法」但和仓库已有测试或文档冲突；题面引用外部规范（GNU 手册、no-color.org、RFC）；仓库里已有同类条件判断先例（如 X-Forwarded-Proto）。
- 注意：「隐藏」是事后对照答案才确认的，动手前能识别多少要专门验证 —— 这是下一步重点。

### F2 题面说的范围比正确修法窄
**题面只描述一个场景（某平台、某个例子），正确修法要更通用**；DS 照字面改就挂。
- 失败题里：4 道 —— bat-2650（标题「on Windows」）、caddy-6051（空行 vs 只有空白的行）、fpm-1829（例子比标题窄）、fmt-3750（非十进制也要分组）
- 做对的题里：2 道 —— laravel-52866、rubocop-13362
- 有该特征时失败比例 4/6 ≈ 67%，远高于整体 18%。
- 动手前信号：标题或例子带限定词（平台、单一例子），而仓库里相关逻辑本来是通用的（如 bat 的扩展名匹配本就跨平台）。

### F1 成对 / 兄弟实现要一起改（偏弱，需收紧）
**正确修法要改两处以上平行的地方**（X 和 ShouldX、读和写、同一方法的多个实现、send 和 csend），DS 只改了一处。
- 失败题里：4 道 —— gin-1957、gson-1100、gson-2061、rubocop-13396
- 做对的题里：10 道（严格算约 7 道）—— 如 lombok 的 Eclipse/Javac 两套实现、gson 多个适配器、rubocop-13424 的 send/csend
- 有该特征时失败比例 4/14 ≈ 29%，只比整体高一点 → **规律收得还不够紧**。
- 收紧方向（待验证）：失败的 4 道里「另一半」都**没在题面里提到**，且在**不同方法 / 不同类**里；做对的题多是仓库里约定俗成的成对结构（lombok 每个功能都有两套实现），DS 熟。下一版按「另一半是否被题面点到、是否同文件相邻」细分。

## 三、两个现象
1. **一过一挂的题**（gson-2061、fpm-1829、bat-2650、rubocop-13396、jq-2728、caddy-6345、preact-4436）：DS 有能力做对，挂的那次是被题面字面带偏或少改一处 —— 更像「题面诱导 + 采样波动」，对应 F2/F1。
2. **两次都挂的题**：多是 F3（隐藏要求）——DS 稳定地按题面理解去做，稳定地和测试期望不一致。
3. 三条特征的线索**大多在仓库里而不在题面里**（兄弟实现、已有测试、手册措辞），支持「决策模型读整个仓库」这一设计。

## 四、局限与下一步
- 样本小：15 道失败，每条特征 4~6 道支撑；结论是候选，不是定论。
- 标注偏差：特征是对照标准答案标的；要用于预测，必须验证「只看题面+仓库」能否识别 —— 下一步让一个不看答案的模型只读题面和仓库去打这三个标签，看和事后标注的一致率。
- F1 需要按上面的方向收紧后重算。
- 主批次跑完（约 267 道）后整体重做一遍，并把剔除清单和本表一起封存。

## 五、补充：只看题面能不能认出这三类（2026-11-14 21:1x）
做法：另一个子 agent 只读 84 道题的题面（看不到标准答案、测试和 DS 结果），给每道题打 F1/F2/F3 的可能性（0~1）。结果文件 `attribution_v1/blind_issue_only_labels.csv`。

| 特征 | 能否认出事后标注（AUC） | 能否直接预测 DS 挂（AUC） |
|---|---|---|
| F1 成对漏改 | 0.76 | 0.43 |
| F2 题面说窄了 | 0.71 | 0.36 |
| F3 隐藏要求 | 0.83 | 0.64 |

（AUC：预测打分准不准，0.5 = 瞎猜，1 = 全对；样本 84 道、其中 15 道挂，置信区间很宽。）

读法：
1. 只看题面，**能大致认出**这三类特征（0.71~0.83），说明特征本身不是「只能事后看出来」。
2. 但拿题面打分直接去猜 DS 挂不挂，只有 F3 有一点信号（0.64），F1、F2 反而低于 0.5——因为只看题面会把很多题都判成「有这个特征」（84 道里 F1 判了 42 道、F3 判了 50 道），区分不出哪些真的会让 DS 挂。
3. 结论：**光读题面不够，必须读仓库**（看兄弟实现在不在、已有测试和题面是否冲突），这正是方法里「决策模型读整个仓库」那一步要解决的。下一步：同样的打分加上仓库内容再测一次。
4. 注意：子 agent 说有几道长题面读的时候被截断到 1500 字，结果偏保守。

## 七、补充：「题面 + 仓库」一起读能不能分出 DS 会挂的题（2026-11-14 23:5x）
做法：每道题按出题时的基线版本做一份代码快照（删掉 git 历史，看不到未来提交），3 个 Sonnet 子 agent 只读题面和快照，给 F1/F2/F3 和总体难度 p_hard 打分；每行必须引用实际读过的文件（84 行全部有引用）。结果 `attribution_v1/blind_repo_labels_v2.csv`。
（第一次尝试用的是按需下载内容的克隆，代码检索大量超时、多数题没真读到代码，已作废重做。）

| 打分 | 只看题面 AUC | 题面+仓库 AUC（95% 区间） |
|---|---|---|
| F1 成对漏改 | 0.43 | 0.39（0.25~0.55） |
| F2 题面说窄了 | 0.36 | 0.50（0.34~0.65） |
| F3 隐藏要求 | 0.64 | 0.66（0.49~0.81） |
| 总体难度 p_hard | — | 0.61（0.44~0.77） |

（84 道，15 道挂；AUC 0.5 = 瞎猜。）

读法（如实写）：
1. **加上仓库后只小幅变化，区间都跨 0.5，统计上没有可靠的提升**。F3「隐藏要求」仍是唯一稳定有点信号的特征。
2. 原因猜测：①子 agent 每题只做 3~10 次检索，读得浅；②特征定义还是太宽（把很多做对的题也判成高风险）；③失败样本少（15 道），区间很宽。
3. 下一步（按性价比）：
   - 把 F3 收窄成更可检的子型：「题面写的期望 / 表格 与仓库现有测试或文档冲突」，让决策模型逐条去找冲突证据，而不是给笼统分数；
   - 换更强的决策模型、读得更深（方法设计里本来就允许慢而强）；
   - 等 DS 失败样本攒到 40+（主批次 + Pro）再重测，区间才收得住。

## 八、强模型完整决策流程（Opus + 查证清单，2026-11-15 00:0x）
做法：Opus 当决策模型，按 `attribution_v1/decision_checklist.md` 五步逐题查证（定位 → 期望冲突 → 范围 → 兄弟实现 → 改动规模），每条结论带「文件:行号」；只读题面和无历史的代码快照；每题 10~20 次检索。结果 `attribution_v1/decision_opus_armC.jsonl`（84 道，全部有证据）。

| 打分 | Sonnet 浅读（上一轮） | **Opus 清单深读** （95% 区间） |
|---|---|---|
| 隐藏要求 risk_hidden | 0.66 | **0.74（0.62~0.86）** |
| 题面说窄了 risk_narrow | 0.50 | 0.66（0.55~0.77） |
| 成对漏改 risk_sibling | 0.39 | 0.60（0.45~0.75） |
| 综合失败概率 p_fail | 0.61 | **0.74（0.61~0.85）** |

（84 道、15 道挂；AUC 0.5 = 瞎猜。p_fail 排前 15 的题里有 6 道真挂，整体挂率 18%。）

读法：
1. **第一次区间整体高于 0.5**：换强模型 + 按清单逐条查证后，「隐藏要求」和综合判断都有了统计上站得住的信号；说明上一轮没提升主要是「读得浅」，不是仓库没用。
2. **重大保留：决策模型可能「记得答案」**。这些都是公开题，几个子 agent 自己承认部分判断靠「回忆上游当年怎么修」（如 jekyll-8771、gin-1957 的推断）。这会把准度抬高。必须做的对照：
   - 同一流程加一条硬性要求「不得使用对上游修复的记忆」，重跑比较；
   - 在决策模型训练截止之后才出现的题（或冷门仓库）上测——SWE-bench Pro 盲测组 / 新抽的题。
3. 排名前列的误报（jekyll-8771、lombok-3674、gson-2479、carbon-3005 都被判高风险但 DS 两次都过）说明「改动大 / 要求精确」不一定难倒 DS——DS 在多文件题上比预期强，后续要校准。

## 九、控制变量：是模型变强了，还是信息变精准了？（2026-11-15 00:3x）

crc 问：上一节从 0.61 升到 0.74，同时换了模型（Sonnet→Opus）和提示（笼统打分→5 步查证清单），分不清功劳。做 2×2，每格只差一个因素：同一批 84 道（15 道 DS 两次都挂）、同一份代码快照（基线版本、无历史）、四格都加「不得使用对上游修复的记忆」。

| AUC（95% 区间） | 笼统打分 | 查证清单 |
|---|---|---|
| Sonnet | 0.58（0.42~0.73） | 0.71（0.56~0.84） |
| Opus | 0.63（0.47~0.78） | 0.69（0.56~0.81） |

成对自助抽样（同一批题重抽 3000 次，算差值）：
- **提示的主效应**（清单 − 笼统，两模型平均）：+0.09（0.01~0.18），99% 的重抽里为正。
- **模型的主效应**（Opus − Sonnet，两提示平均）：+0.02（−0.07~0.11），62% 为正 ≈ 没差别。
- 用清单时 Sonnet 0.71 ≈ Opus 0.69：清单把便宜模型拉到和强模型同一水平。

结论：**提升来自「信息变精准」（按清单逐条去仓库里查证），不是模型变强。** 后续决策模型可用 Sonnet + 清单，成本更低。

旁证：
- 不读代码只看题面的 Sonnet 笼统打分：0.41（0.26~0.57）——读仓库本身是必要条件（这份是子 agent 没按要求读快照、作废后重跑留下的意外对照）。
- 禁用记忆对 Opus+清单的影响：0.74 → 0.69；剔除自报「想起过上游答案」的 6 道后 0.70。

保留：
1. 84 道、只有 15 道失败，区间宽；这批是提炼组（mining），不是盲测。最终要在冻结预测后的盲测组上复核。
2. 两种提示输出的分数字段不同（清单出 p_fail，笼统出 p_hard），都是「失败概率」含义。
3. **记忆泄漏**：主会话长期记忆里写过部分题（如 gin-1957、micropython-12158）的历史结果，子 agent 启动时能读到。本次结论不受影响（剔除后不变），但以后正式盲测必须让决策模型在读不到长期记忆的环境里跑。

数据：scratchpad 下 dm_N_part1-4.jsonl、dm_SC_half1/2.jsonl、og_half1/2.csv、sg_half1/2.csv；计算脚本 auc2x2.py。
