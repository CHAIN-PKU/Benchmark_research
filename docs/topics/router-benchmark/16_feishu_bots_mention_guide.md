# 飞书群里两个机器人如何互相 @、互相通话（给另一边的说明）

写这份的人：DSH（本群机器人之一）。我们这边两个机器人（DSH、Claude Code）可以互相
看到并回复；另一边说「不能有两个机器人、不能 @ 彼此」，下面是原理、两条可行路线和坑。

## 一、先搞清 4 个事实

1. 飞书里的「机器人」= 一个自建应用的 bot。**一个应用只有一个 bot**；两个机器人必须
   是**两个不同的应用**，各自有自己的 app_id / app_secret / open_id。
2. 飞书消息里的「@」是**结构化字段**，不是文本。只有消息内容里带 at 标签，才会生成
   `mentions` 数组、才会触发「被 @」的通知事件。纯文本里写「@某某」对方**收不到通知**。
3. `open_id` 是**应用级隔离**的：同一个群、同一个成员，在 A 应用看到的 open_id 和在 B
   应用看到的 open_id 不一样。把一个应用的 open_id 拿到另一个应用去 @，会报
   99992361（open_id cross app）。
4. 机器人能收到什么消息，取决于它的**权限 + 事件订阅**：只订阅「@我」的话，只能收到
   真正 at 到它的消息；要收到群里全部消息，需要开「读取群消息」的权限/事件。

## 二、为什么我们这边能「互相通话」

我们两个 agent 用的是**轮询全量消息**，不是靠飞书 @ 通知：

- 每个 agent 用自己应用的权限，定时调 `GET /open-apis/im/v1/messages?container_id_type=chat&container_id=<chat_id>`
  把群消息拉下来；
- 文本里写的 `@claude` / `@DSH` 只是**我们自己的约定**，飞书并不认为那是 at；
- 两个 agent 都能读到全部消息，所以都能看到对方的「@」并回复。

这条路最简单，不依赖机器人之间的 @ 通知；代价是每个 agent 都要有「读取群消息」的权限。

## 三、路线 A：轮询全量消息（推荐先走这条）

每个机器人各自做：

1. 在飞书开放平台建**自己的自建应用**，开启「机器人」能力。
2. 权限至少开：
   - `im:message`（发消息）
   - `im:message.group_msg` 或等价「读取群消息」权限（拉全部群消息）
   - `im:chat:readonly`（读群信息/成员，可选）
3. 事件订阅（如果用事件方式）：`im.message.receive_v1`，并在事件配置里勾选
   「机器人接收群组中所有消息」（不同版本界面叫法略有差异）。
4. 把机器人**加进群**（群设置 → 机器人 → 添加）。
5. 程序里定时拉消息；用发送者名字/约定前缀（比如【BOT-A】/【BOT-B】）区分谁说的话。
6. 回复时直接发文本消息即可。

## 四、路线 B：真正的 @ 通知（需要结构化 at）

如果你确实要「@ 到对方、触发对方的事件」，按下面做：

1. 每个机器人用**自己的应用**查群成员，拿到**自己应用视角下**对方的 open_id：
   `GET /open-apis/im/v1/chats/{chat_id}/members?member_id_type=open_id`
   （返回里 `member_id_type=open_id` 的成员，包含机器人在群里的成员记录）。
2. 发消息时用 at 标签。文本消息：
   ```json
   { "text": "<at user_id=\"ou_对方的open_id\"></at> 你好，轮到你跑了" }
   ```
   富文本（post）：
   ```json
   { "zh_cn": { "title": "", "content": [[
       { "tag": "at", "user_id": "ou_对方的open_id" },
       { "tag": "text", "text": " 你好，轮到你跑了" }
   ]] } }
   ```
3. 注意：有资料表明飞书的「消息事件推送」**可能不推送其他机器人发的消息**（防止机器人互相触发死循环）。
   如果实测确认如此，那么路线 B 的 at 标签只解决「给人看/手机提醒」，机器人之间仍要靠路线 A 的轮询来读到消息。
   所以最稳的组合是：**轮询读消息（必须） + at 标签做提醒（可选）**。下面是订阅事件的写法，供实测可用时使用：
   接收方订阅 `im.message.receive_v1` 事件，事件体里的 `mentions` 数组会带
   `id.open_id`（这是接收方应用视角的 open_id），拿它和自己的 bot open_id 比，
   相等就是「@ 我」。
4. 关键点：**发送方查、发送方用**。不要跨应用复用 open_id（99992361）。

## 五、常见坑（另一边的症状多半在这里）

1. 两个「机器人」其实是**同一个应用**的两个实例 → 飞书只认一个 bot，不能互相 @。
   解决：拆成两个应用。
2. 只写了「@名字」的纯文本 → 没有 `mentions`、没有通知。解决：用 at 标签，或改轮询。
3. 用 A 应用查到的 open_id 在 B 应用发 at → 99992361。解决：各查各的。
4. 机器人没被加进群 / 没开「读取群消息」→ 只收 @ 消息，读不到上下文。解决：加群 +
   补权限和事件。
5. 没开 `im:message:send_as_bot` → 发不出消息。解决：补发消息权限。
6. 群或租户设置里禁用了机器人互相 @ / 外部群限制 → 需要群主或管理员在后台放开。

## 六、给另一边的最小落地清单

1. 建两个自建应用，各开机器人能力；
2. 各开 `im:message`、`im:message.group_msg`（读群消息）、`im:chat:readonly`；
3. 订阅 `im.message.receive_v1`，勾选接收群内所有消息（或只用轮询拉取）；
4. 把两个机器人都加进同一个群；
5. 程序定时拉取全量消息，按约定前缀识别对方、回复；
6. 若要真 @：各应用自己查群成员的 open_id，用 at 标签发消息；不要跨应用复用 open_id。

## 七、我们这边的实现参考

- 工具：`ops/feishu-bridge/bridge.mjs`（拉消息、发消息、解析 mentions）
  - `pull` 输出里每条消息带 `mentions`/`mentioned_me`；
  - 发送用 `send` / `reply`，文本消息；
  - 我们靠「双方都拉全量消息 + 文本约定」实现互相通话，不依赖飞书 @ 通知。
